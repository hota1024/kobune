# Minato とは

Minato は、git worktree ひとつひとつに動いている環境を与え、それぞれに URL を
割り当てます。

```console
$ minato new feature/user-auth
  ✓ creating worktree feature/user-auth
  ✓ starting web
  ✓ waiting for web

myapp / feature-user-auth  (feature/user-auth)
  web   ready     https://web.feature-user-auth.myapp.localhost
```

考え方はこれだけです。worktree 1 つに環境 1 つ。worktree が生まれれば環境が
生まれ、消えれば消える。ほかに覚えることはありません。

## 何を解決するのか

レビューのためにブランチを切り替えるには、動かしているものを止め、切り替え、
立ち上がるのを待ち、作業の続きを見失う必要があります。複数のブランチを同時に
動かそうとすれば、空いているポートを探し、どれがどれか覚え、共有された状態に
つまずくことになります。

ソースコードの側は worktree がすでに解決しています。Minato が解決するのは、
それを「動かす」側です。

- **worktree ごとに URL が生えます。** ブランチ名から作られるので
  `feature/user-auth` は `web.feature-user-auth.myapp.localhost` になり、
  再起動しても変わりません。
- **使われていない環境は自分で止まり**、次のリクエストで 1〜2 秒で起き上がり
  ます。worktree が 10 個あっても、動いているスタックが 10 個にはなりません。
- **衝突しません。** コンテナも URL も別々で、データベースのように共有したい
  ものは設定に一度書くだけです。

## エージェントが操作することを前提に

これが設計の大部分を決めています。あなたのコードを触る AI エージェントは、
自分の変更が動いたかを確認する必要があります。ところがよくあるやり方 ——
`docker` を直接叩き、ポートを推測し、curl する —— は、気づきにくい形で
失敗します。

そこで、すべてのコマンドが `--json` を話し、すべての失敗が「どういう種類の
失敗か」を表す終了コードを返し、`minato skill install` が「どのコマンドを
使い、何を避けるか」を書いた Skill ファイルを配置します。それに従う
エージェントは `docker` を直接触らず、ポートを推測せず、何かがおかしいときに
空の応答ではなく本物のエラーを受け取ります。

だからといって人が使いにくくなるわけではありません。同じコマンドが、人が読む
ときには JSON なしで同じ情報を出します。

## Minato ではないもの

- **本番向けのデプロイツールではありません。** すべては開発マシンと、その
  持ち主がいることを前提にしています。
- **コンテナランタイムではありません。** その仕事は Docker や Apple Container
  がします。Minato はそれを取りまとめるだけです。
- **compose の置き換えでもありません。** 1 ブランチに 1 スタックで足りるなら
  compose のほうが単純で、そのまま使うべきです。Minato が効いてくるのは
  ブランチが増えてからです。
